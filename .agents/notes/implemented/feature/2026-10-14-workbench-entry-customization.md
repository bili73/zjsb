# Agent Note: Customizable workbench entry layout

Status: implemented
Scope: frontend/src/components/UploadPanel.vue, frontend/src/useDragReorder.ts, frontend/src/workbenchEntries.ts, frontend/tests/workbench-entries.test.ts
Last-verified: 2026-10-14

## Problem

The workbench renders one card per supported material type (twelve today); every future type adds another card until the grid gets crowded. The user asks for operator-customizable entries: choose which types sit on the workbench (max 12), reorder them, and tuck the rest away while keeping them reachable.

## Decision

Split the type-card grid into an ordered visible set plus a tucked set. Customization is an on-grid edit mode: 自定义入口 toggles it, and the actual workbench cards become directly manipulable — long-press (~280 ms, 10 px slop) picks a card up, the card follows the pointer and swaps with whichever card it passes (swap semantics per user request), each card shows a top-right ✕ that tucks it, and when fewer than 12 entries are visible a dashed 「+」 slot appears after the last card. The section title 选择材料类型 was dropped after feedback that it wasted vertical space (the goal of tucking is a compact first screen with 开始识别 visible); the tools row (收纳箱 toggle in edit mode, 恢复默认/完成) sits right-aligned in its place. Tucked types no longer render as an always-expanded section under the grid in edit mode ("收纳箱真的蠢，能不能收起来") — the 「+」 slot (relabeled 点击添加类型) opens the same 收纳箱(N) floating popover on click, and tucked cards there are click-to-add (primary path per user feedback; long-press drag to the 「+」 slot still works as the precision path). A drag that ends with pointer capture re-targets the up event to the origin card, so its trailing click is swallowed (suppressTuckedClick, reset on the next pointerdown) and addEntry is idempotent (skips keys already in the layout) — a drag-add can never double-append. The popover (absolute, top-right of the section, two-column compact cards without descriptions) closes via its ✕, the toggle, exiting edit mode, or automatically when the tucked set empties. Non-edit mode keeps the collapsed 更多类型 details. Pointer-events-based (no dependency); the dragged card is pointer-events:none so hit-testing sees the card beneath. 恢复默认/完成 live in the edit-mode header; the earlier two-pane dialog with HTML5 list DnD was replaced after user feedback ("点击自定义入口时，工作台上的卡片可以直接在网格上被长按拖动").

Drag motion hardening after the first on-grid version stuttered and froze ("卡片交换位置的动画不够流畅，多交换两次界面就会卡死"): the first version ran elementFromPoint + a full section re-render + a forced reflow on every pointermove with no guard, so a pointer parked on the seam between two slots re-hit the alternating card each event and oscillated A↔B swaps, starving the main thread. Now pointermove only records the pointer and schedules one rAF per frame (follow-pointer write + elementFromPoint read paired in the same frame); swaps carry a cooldown — the pointer must travel SWAP_REARM_PX (14 px) from the last swap point before the next swap — which deterministically kills the oscillation. Smoothness: displaced cards FLIP-glide to their new slots (capture rects before the reorder, inverted transform + forced reflow, then a `.card-flip` transition to identity; in-flight glides are flushed before the next capture or drag start so rect reads stay clean); on release the dragged card glides from its visual position into its slot (settleCard) instead of snapping; follow uses translate3d + will-change for compositing; in-flight FLIP rects are read in one batch before gliding. Visual verification exposed two more defects the first version shipped silently: (1) gliding cards still sit under the pointer mid-flight, so the next frame re-hit them and instantly swapped back (revert) — hit-testing now ignores `.card-flip` cards until they land; (2) pointer capture is lost when Vue moves the dragged DOM node to its new slot, so card-attached listeners stopped receiving pointerup and the drag state leaked as an un-interactable zombie overlay — move/up/cancel listeners now live on window, filtered by pointerId, with detach on unmount. An adversarial review then confirmed a multi-pointer race class (touch/pen): a second pointer landing on another card during the hold or drag used to detach the first pointer's window listeners, clobber the shared holdTimer, and permanently orphan a card in `.dragging-edit`; and 完成 clicked mid-hold left an armed timer that started a drag after edit mode exited. Enforced a single-drag invariant instead: a card pointerdown while any gesture is armed or dragging is ignored (windowDetach/draggingKey guard), the hold timer re-checks editMode, and exitEditMode clears the timer and detaches the window handlers. After the interaction settled, the whole mechanism was extracted verbatim into the reusable composable `src/useDragReorder.ts` (long-press arming, pointerId-filtered window listeners, rAF batching, swap cooldown, FLIP glide + settle, single-drag invariant, Node-safe guards); UploadPanel only supplies getOrder/setOrder/enabled and the 「+」 drop-slot callbacks. The drag/glide CSS classes moved from this component's scoped styles to global style.css as `.drag-reorder-dragging`/`.drag-reorder-flip` so other grids can adopt them; the mechanical knowledge (iron rules + Playwright verification recipe) is packaged as the local skill `.claude/skills/card-drag-reorder/SKILL.md`. Post-extraction bug: after 恢复默认 (layout back to the null "never customized" sentinel), the ✕ handler indexed into `layout.value ?? []` — an empty base — so tucking one card wrote an empty layout and cleared the whole grid, and the composable's getOrder likewise returned `[]` which silently disabled drag swaps. Both now fall back to the full catalogue order (`layout.value ?? catalogueKeys.value`), and removeEntry works by key instead of index. The layout persists in the browser's localStorage under `ocr-workbench-entries-v1` as a JSON array of doc_type keys; parsing failures or malformed records fall back to the default (all types, catalogue order). Once a customization exists, catalogue types not listed stay tucked — future backend types default to tucked, which is the crowding motivation. Stale keys of retired types are purged from the stored layout when the catalogue loads non-empty; the first catalogue load (empty list) never rewrites storage. Pure logic lives in `src/workbenchEntries.ts` (`splitEntries`, `loadWorkbenchLayout`, `saveWorkbenchLayout`) and is unit tested. If the currently selected type is tucked with no files chosen, the selection moves to the first visible entry; with files chosen the selection is kept.

## Persistence decision update

The [account-layout change](2026-10-14-account-workbench-layout.md) replaces the shared localStorage persistence described above with self-only server persistence and explicit save. Dragging, tucking and catalogue splitting remain. The original browser-storage choice and reasons remain here as historical context.

## Alternatives considered

- Server-side per-account preference (settings API): survives browser switches but adds a contract, migration and auth surface for a personal layout preference; localStorage matches the LAN single-machine usage. Revisit if operators roam machines.
- Drag-and-drop reordering: initially skipped for focus/touch pitfalls, then implemented at the user's explicit request using native HTML5 DnD (no dependency), with the insertion indicator and the buttons retained as the keyboard/precision path.
- Hide tucked types entirely: smallest grid, but operators would lose discoverability of rarely used types; the collapsible section keeps them one click away.

## Verification

Frontend typecheck, node tests and production build pass; `npm run verify` passes with this note. Node tests cover default/full display, unknown and duplicate keys, the 12-entry cap, storage roundtrip, malformed storage fallback, null-save clearing and quota-failure tolerance.

## Consequences

The layout is per browser profile, not per account: switching machines or clearing site data resets to the full grid. New types land tucked for customized browsers, so release notes should mention where to find them. `splitEntries` silently drops unknown keys, so a retired doc type cannot break rendering. No API, permission or server-storage change.

The [twelve-visible-card correction](../bug-fix/2026-10-14-workbench-twelve-visible-cards.md) enforces12 visible entries for every layout independently of the13-type catalogue. Existing13-key preferences remain readable; excess cards are hidden rather than removed. This supersedes the interview extension display-cap increase, retaining the wire compatibility and original account rules.
