# Agent Note: Replan photo-table conversion from the verified 1.22.3 baseline

Status: implemented
Scope: backend/ocr_app, frontend/src, tests, frontend/tests, scripts, SPEC.md, openapi.yaml, FRONTEND_FIELDS.md, RUNTIME.md
Last-verified: 2026-10-14

## Problem

新增“表格转 Excel”入口，将工作人员拍摄的表格恢复为可核对、可修改的电子表格。识别需要处理照片方向、表格主体、标题、表头、空白单元格和合并关系，不能只得到一段 OCR 文字。所有类型 Excel 的表头与数据字体统一为微软雅黑 12 号；新增照片表格的顶部标题为微软雅黑 21 号。

用户要求撤回上一轮未提交的实现并重新设计。源码基线恢复为 `c4da709d599dd7361194d2c407b890ba55f199ff`（应用/API 1.22.3、SPEC v1.28）。上一轮方案转为[撤回记录](../../rejected/feature/2026-10-13-photo-table-to-excel.md)，用户于2026-10-14确认实施；先通过阶段A资格试验再接入业务。

## Verified facts

- 当前程序已经有 GLM、Paddle 的独立模型队列、图片方向判断、普通 CPU OCR、版本绑定审核、原件预览和 Excel 导出。新增材料类型不等于新增模型。
- 当前 Windows `RuntimeConfig.model_command()` 仍选择 `paddleocr-vl` 环境和默认权重。另有 1.6 的历史试验记录，但不能因为已安装就把生产版本描述成 1.6。本功能沿用当前配置，试验记录实际 checkpoint/revision。
- 现有 `table_format.py` 能将 OTSL 转为 HTML，保留空格位和合并拓扑；它不是完整的任意表格业务协议，正确解码也不证明识别完整。
- 四张素材都是有线框的签到表：各有 10 列、1 行表头，框内分别有 7、4、10、18 行数据。部分行被划除，存在手写签名；第三张表框下方还有一条手写补录。不能把这条补录默认为无关文字。
- 历史 CPU 预检定位到四个主表，但第四张列数估算为 8。该结果说明线检测只能提供候选，不能用它强制裁掉模型输出的其余列。上一轮没有真实模型 OCR 验收。
- 现有 `TaskScheduler` 按体检/其他材料分两条任务通道。表格如果使用 Paddle，必须同时检查任务通道归属，不能只改 `pipeline.py` 中的模型名。
- 普通批次当前不能追加文件；现有追加接口专属于人员材料包。首版纠正裁剪可沿用银行卡“裁图后新建任务”的方式，不顺手放宽旧追加接口。

## Goal and acceptance

工作人员上传照片，系统自动建议主体、标题和表头，并输出真实单元格矩阵；用户对照原图修改后，导出内容应与保存的表格逐格一致。没有识别出的文字允许补录，真实空白保持空白。原件、初始 OCR 和人工修正分别保留，失败不能悄悄变成一张看似完整的 Excel。

阻断问题：None (0)。模型表现、软超时和自动分片是否有益，属于第一阶段实测要回答的问题，不凭假定直接写成已完成能力。

## Assumptions

1. 首版输入为单张 JPG/PNG/HEIC 照片；本轮不做 PDF 表格、跨照片续表自动拼接。格式限制在上传前后均明确校验。
2. 表格是任意业务表格，不预设“姓名、部门、签到”等固定列；样本答案和人工画框不能喂给自动识别流程。
3. 不安装、不下载、不升级识别模型。Paddle、GLM、方向模型及 RapidOCR 均复用仓库已有资产；CPU 辅助工作在受监督的任务进程中执行，不新增常驻服务。
4. 一张照片选择一个主体，导出一个以确认后的标题命名的 XLSX；多张照片导出 ZIP。多个候选表保留供选择，其他表不无提示地被丢弃。
5. 沿用现有单任务 180 秒硬预算和取消机制；推理、等待和重试共同消耗预算。单次生成软预算在实测后确定，不用延长总超时掩盖截断。
6. 现有证件、体检、人员材料包的业务字段与导出条件继续适用。全局字体调整只影响 Excel 样式，不改变字段、日期含义和现有底色/对齐；新增表格表头用 `#ef760e`。
7. 首版沿用现有结构解码上限（最多 1,000 行、200 列、10,000 格），超限明确失败并保留可恢复结果；不得截取前若干行后声称完成。

## Decision

### 1. 先证明真实样本可以恢复，再接入业务

先写独立资格测试脚本，读取四份原件，冻结主体范围、标题、表头、框内行列、划除行及表外补录的人工参考。手写内容分为“可辨认”和“无法可靠辨认”；后者单列，不靠姓名列猜签名。模型运行时不能读取这些答案。

使用现有受监督 runtime，单模型驻留、逐份执行；需要比较 GLM 时顺序切换。测试使用独立加密目录，不挂生产任务库。当前服务若占用 GPU，应在活动任务和排队均为空时按既有流程备份、暂停、测试并恢复服务，不与现有模型进程争用 GPU。失败和超时输出也保留。

先测“自动校正后的整张照片”和“自动定位的整表区域”，选择实际表现更好的最小流程。连续行带分片只作为截断后的试验方案；必须证明不会切断合并格、重复/漏掉行后才能采用，不能根据预估行列数强行拼表。记录具体提示词、checkpoint、预算和输入哈希，测试结果不能沿用上一轮单元测试数量冒充。

### 2. 主体、标题与表头分别处理

- **方向**：先 EXIF，再复用现有方向判断和保守扶正；判断不足保留原方向。整页预览与 OCR 输入使用同一校正决定。
- **主体**：OpenCV 线框只产生候选，结合已有 CPU OCR 的文字分布区分主表与上方告示框。保留候选范围和完整原图；多个相近候选提示用户选择。只有边界可靠时对表格裁图做透视校正，并记录坐标变换。
- **标题**：从主体上方邻近文本中给出候选，保留来源位置；不固定取最后一行，不写死“签到表”。无法确定就留空待填。标题作为文件名/工作表名，并在照片表格工作簿顶部独立一行展示；原始矩阵从第二行写入，不将标题算入表头。
- **表头**：先采用模型明确的表头标记，再结合首部行、合并关系与位置给建议；支持多行表头。没有可靠依据时要求选择表头行数，不能把第一行数据直接当表头。

表头自动填写的交互调整见[有依据的表头行数自动填写](2026-10-14-auto-table-header-rows.md)；该篇单独记录原手动采用建议的变化，其他流程继续由本篇约束。入口显示名称按用户后续要求简化为“表格”。
- **表外内容**：完整原图一直可见；邻近表格的额外文字保留为待核对片段。第三张样本的手写补录需要可见提示，由用户决定补成一行还是忽略。仅有线框完整不能声明整张照片内容完整。

### 3. 结构识别与异常恢复

默认由当前 Paddle 执行 `Table Recognition:`，复用 OTSL 解码并严格解析 HTML 表格。只有空输出、结构无法解析或明确截断等情形，才在剩余预算内试已有 GLM；两次输出独立保留，不自动把不同模型的相邻单元格拼成一条记录。

结果使用动态矩阵：`rows: string[][]`、独立 `merges`、表头建议与标题候选。空格位必须保留；重复值属于不同格位，不去重。合并覆盖已有文字、越界跨度、不完整标签、结构与可见线框明显冲突，都产生具体提示。几何行列估计只用于提示，不能删除多出的识别内容。

模型不提供可信字段概率时，`confidence` 保持不可用。低质量手写、划除行和模型终止原因用质量提示表达，不能编造“95%置信度”。划除行保留，由用户处理；表格 OCR 不解释人员业务状态。

表格与体检共用 Paddle 任务通道；证件继续走现有通道。单驻留模式仍串行，备用模型请求进入其已有队列，不新建模型服务。进度显示真实阶段和已完成的区域数，不使用时间推算的百分比。

### 4. 原图对照与人工修改

详情页左侧完整原图与主体框，右侧表格草稿；标题、表头行数、单元格、行列和合并关系都可修改。按选中位置插入/删除行列，删除有内容的区域需确认；合并不允许覆盖非空格。支持键盘换格、滚动查看和保存草稿，避免只提供“删除末行/末列”。较大结果分批显示，导出始终读取全部保存行。

普通文字补录继续使用已有“框选识别→编辑/复制”能力。主体选错时提供调整裁剪并新建表格任务的入口，明确标注新任务，保留旧结果；首版复用银行卡恢复上传方式，不扩展人员包追加权限。

保存继续绑定 `run_id` 和 `expected_revision`。使用 `reviewed_tables` 保存人工版本，初始 `tables` 与原始尝试不改写；切任务、换账号、版本冲突或迟到识别结果不能覆盖当前草稿。权限沿用操作员本人/管理员全量/只读不可写。

### 5. 导出与 Excel 样式

后续[免首次保存导出](../../implemented/simplification/2026-10-14-table-export-without-confirmation.md)部分替代本节的强制保存门禁，其他来源、格式与完整性约束继续有效；以下保留初版取舍。用户随后将所有Excel数据底色统一白色，表头配色不变。

导出前检查已保存的标题、明确的表头范围、有效的矩阵和合并关系；真实空白不要求填满。对于截断等不完整输出，用户需要补齐或明确确认仅保留当前结果，不能用“有两行数据”推断识别完整。已有证件/体检的必填值规则不因此收紧。

一个任务生成一个 XLSX；批量生成 ZIP，重名自动加序号。工作簿所有单元格值与保存结果一致，编号前导零、日期/时间原文和换行保留；以 `=` 等开头的 OCR 内容按文本写入。文件名过滤不合法字符，工作表名遵守 Excel 长度和字符限制。

按用户2026-10-14修正，所有导出类型应用微软雅黑12号表头和数据；新增照片表格顶部独立标题行使用微软雅黑21号，既有业务工作簿不新增标题行。新增表格表头填充 `#ef760e`；旧业务表格保留原底色和对齐，体检项目数量居中的既有规则继续生效。列宽、自动换行与行高同步调整，不能只放大字体而截住表头。

### 6. API 与落盘边界

材料目录新增 `TABLE`，但不进入人员包自动分类、人员包上传或固定“必填字段设置”。前后端都校验这些边界。表格字段采用独立 `PhotoTable` 契约，不伪装成证书字段；包含稳定的 `table_id`、来源页/区域、原始矩阵、合并信息、标题/表头建议与质量提示。

复用当前上传、任务查询、审核与导出端点；审核增加显式表格载荷，禁止客户端改写原始来源或指定他人的表格。导出响应说明单 XLSX/批量 ZIP 的媒体类型和 UTF-8 文件名；客户端对异常文件名头安全回退。原图、结果和尝试继续加密，诊断只记录阶段、错误码、数量与耗时。

## Implementation boundaries

`photo_table_pipeline.py`在受监督的任务进程中调用既有预处理/模型队列，`table_recognition.py`负责主体候选、严格结构解码和审核矩阵校验。`TableReview.vue`和`table-review.ts`提供人工草稿，不修改初始识别矩阵。`table_export.py`序列化独立表格，既有业务导出只调整字号/行高。无新增模型、服务或数据库迁移。

照片有多个候选时，用户可定位查看，再裁剪另建任务；同一识别输出含多个表时保留原始尝试，当前仅显示最大表并标记不完整。未做在当前任务内切换主体后覆写结果。连续长线框提示更多行列时只提示复核并要求不完整确认，不据此补造/删除识别值。各行列数不一致时补空格保留已有值，并明确要求核对。

- [独立模型队列](../../implemented/architecture/2026-10-08-independent-model-queues.md)与[账号归属](../../implemented/feature/2026-10-10-account-owned-batches.md)继续约束任务和接口，不旁路它们。

## Alternatives considered

- **直接接完前后端再测模型**：能很快看到入口和导出，普通软件测试也较容易建立。但此次主要风险在真实照片恢复质量，先完成界面会放大返工，采用样本资格测试先行。
- **只用线框数决定行列**：轻量、确定性强、有明确几何解释。现有第四张估计8列而原件10列，不能把此估计当真值裁列；保留为定位与质量提示。
- **只做整图普通 OCR 再按空格拆列**：实现短且不需要结构解码，但空白格、合并表头和手写重叠容易造成错列，采用表格提示与显式拓扑。
- **直接安装完整 Paddle 文档流水线**：有成熟布局和图像处理组合。但会扩大模型、依赖和部署边界，本轮先使用现有能力，试验失败再比较新增方案。
- **默认两个模型每格融合**：有机会补齐单模型漏字，但成本成倍增加且容易把不同列拼错，默认主模型，异常时有界备用并保留各自原文。
- **把同批照片直接拼成一个表**：方便一次汇总，但同名表头不能证明属于同一张续表；沿用每张独立工作簿、批量ZIP。
- **不保留表外文字**：输出干净且省事，但第三张样本有真实补录行；主体表与旁边待核对内容分开呈现，让用户决定归属。

## Verified behavior

- 自动主体定位不能把告示框当业务表；标题、表头与正文来源分开。四个框内矩阵的10列和7/4/10/18行都参与对照，划除行和第三张表外补录单独验证；不得无提示丢行、截列或挪格。
- 人工参考与模型结果分开保存；印刷格、可辨手写格、无法辨认格分别统计。空白格不用于抬高文字准确率，旋转衍生图不作为新增独立样本。
- 原图、原始 OCR 与人工版本均可回查。结构故障、token/time limit、错列和不可辨手写应有可见状态及恢复操作，不能变成静默成功。
- 保存后重开和导出逐格一致；中间插删、合并/拆分、多行表头、选表、改标题、重复文件名及不同账号/版本均有覆盖。
- 所有既有 Excel 表头/数据12号字体生效，新增照片表格标题21号，原业务字段/门禁和样式约束保持；大字号的实际导出通过真实下载的字体/文本断言和渲染检查；渲染工具导入时会把数字样文本显示成数字，原XLSX的前导零及文本类型另行核验。
- 通过相关前后端回归、类型检查、隔离构建、浏览器操作与 DDE 校验；实际识别成绩、运行服务版本和代码完成状态分别陈述。

## Consequences

四张照片只覆盖一种线框表格，不能代表无框表、票据、弯曲纸张或所有手写体。签名本身可能不可辨，自动摆正也不能恢复遮挡。保留来源与人工编辑能控制损失，但不能把识别准确率问题解释成已解决。Mac速度和多人并发需在实际部署环境另测。

## Qualification checkpoint

2026-10-14，现有Paddle单驻留串行完成四张原始照片×整图/自动主体两种输入。自动主体恢复全部4张的行列结构（含表头8×10、5×10、11×10、19×10），8次调用均eos，无超时/截断；主体调用3.140–12.453秒，均值7.082秒，准备时间另记。348个暂定印刷参考格346格一致，7个暂定可辨手写格一致；39个未可靠标注的格单列，不用空白抬高准确率。这是同一版式4张照片、单人暂定参考；两处姓名差异仍需独立复核，不能直接宣称两处均为模型错误。原始参考保持冻结。数据见output/photo-tables-20261014-paddle-v1/，初始参考见output/photo-table-reference-20261014/；原图和OCR结果加密，CSV可用于绘图。

资格结果支持默认采用自动主体裁剪后整表识别；不启用行带分片。生产单次生成软预算40秒（实测主体最长12.453秒，保留余量），总180秒不变。Paddle结构无效或截断才有界尝试GLM。CPU文字候选已覆盖四张标题与第三张表外手写内容，但文字不保证正确。
