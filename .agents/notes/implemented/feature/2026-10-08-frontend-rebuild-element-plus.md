# Agent Note: Rebuild the frontend with Element Plus and a central batch monitor

Status: implemented
Scope: frontend, IMPLEMENTATION_PLAN.md
Last-verified: 2026-10-10

## Problem

The temporary workbench was retired for an independent rewrite; its retirement decision and reconstruction constraints are recorded at implemented/simplification/2026-10-08-retire-temporary-frontend.md. The user asked for a clean, fresh UI using Element Plus or a DingTalk library (choice delegated), with one hard requirement: recognition runs concurrently, so switching to another document type while tasks are in flight must never lose or freeze the current ones. The backend is owned by a separate agent; its files are read-only for this work.

## Decision

- Stack: Vue 3.5 + TypeScript + Vite, Element Plus 2.14 full import with zh-cn locale, pinned exact dependency versions. Composables only (no Pinia, no vue-router), matching ARCHITECTURE.md's composable-first stance for this local tool.
- Concurrency core: `src/monitor.ts` is a central monitor that tracks every batch of the session at once, decoupled from upload-type selection and tabs. It polls /batches every 2s while any task is in a running status and self-stops otherwise; page-hidden stops, visibility returns restart. Read polling and write actions use separate abort controllers — a slow upload, cancel or rerun never freezes status updates (the retired UI stopped its read loop during writes). Submit inserts an optimistic entry before the list catches up; a batch that just left PROCESSING gets one final task fetch so rows cannot freeze on the last running snapshot; older pages append behind newest-first order.
- Response guards retained from the retired client and extended: `report_grade` is now an accepted abnormal_basis (the retired itemValid whitelist rejected it, misjudging valid backend payloads as INVALID_RESPONSE), `Task.batch_id` is validated when present, optional medical fields (risk_grade, diagnosis, value_num, ref bounds, deviation, diagnosis_sources) and report-summary contradiction checks are guarded. Guards never invent state.
- Medical view switching uses the server-side `items_filter` (all/abnormal/unknown) as the primary control so counts stay on the full-report口径; local search and review-only checkbox are explicitly projections over returned items only.
- Security model preserved: key only in the X-API-Key header and page memory, cleared on logout/unmount; diagnostic cards never contain message, filename, URL, body, headers, key or material values; masked server values stay masked; local original previews stay in page memory for a bounded rolling window and never claim a backend reveal.
- Engine status is a shared composable feeding both the header badge and the engine page; /health is fetched unauthenticated with parse guards and 1s auto-refresh only while startup/stopping is in progress.

Post-delivery adjustments (same day, user feedback): (1) local previews now retain the last five batches with a rolling cap (oldest batch's blob URLs revoked on eviction; everything revoked on logout/unmount) so comparison originals survive switching document types; HEIC render failure shows an explicit fallback message since desktop Chrome/Edge may not render HEIC. (2) Switching the type card while files are pending asks for confirmation and clears them — one batch carries exactly one doc_type_hint, and the user hit precisely that mixed-batch misprocessing (medical files chosen under 体检报告 then submitted after switching to 毕业证 were processed as DIPLOMA); two independent submissions are unaffected, so a reproduced misclassification after this fix would point at the backend hint handling. (3) Six additional UI types were added ahead of backend support (银行卡/身份证/护照/户口本/营业执照/通用识别, keys BANK_CARD/ID_CARD/PASSPORT/HOUSEHOLD_REGISTER/BUSINESS_LICENSE/GENERAL), visibly tagged 后端跟进中; uploads of these currently fail with UNSUPPORTED_DOC_TYPE as expected. This supersedes the old "不接银行卡" boundary by explicit user decision — SPEC.md/openapi.yaml updates belong to the backend agent, not this note.

## Alternatives considered

The [shared required-field settings](2026-10-10-configurable-required-fields.md) make required sets administrator configurable by material type for current and historical tasks. Existing tables are defaults; uncustomized types retain conditional rules. Current metadata, review and atomic export use the same persisted policy. Config revision is separate from task revision, and settings changes preserve OCR/manual values and ciphertext. This partly overlaps the required-field source without superseding presence-only export, monitoring, permissions or evidence preservation.

Administrator listing/creation is now implemented and qualified in [admin account creation](2026-10-09-admin-account-creation.md), with formal HRSSC provisioning and version1.15.0 activation; the earlier CLI-only and proposed snapshots above remain historical. Reset/disable stays CLI-only. Synthetic browser acceptance verifies creation, duplicate rejection, a new viewer's permissions and refresh restoration.

- DingTalk's component library: its Vue desktop ecosystem is weaker and more mobile-oriented; Element Plus is the mature Chinese-desktop admin library and continues the retired Vue lineage. Element Plus chosen.
- Pinia + vue-router: extra state/router layers for a three-tab local workbench; the monitor composable already owns cross-tab shared state. Composables only.
- Keeping the retired single-selected-batch Workspace pattern: it is the root cause of the task-loss complaint — switching selection abandoned the previous batch's live tracking. Replaced by the central monitor.
- Local-only medical filtering (retired behavior): server items_filter keeps abnormal/unknown counts consistent with full-report statistics; local filtering alone misreads coverage.
- Tree-shaken Element Plus via unplugin icons/styles: smaller bundle but build complexity; full import accepted for a local tool (~1 MB minified, 337 KB gzip).
- Parallel upload transfers: serialized per click with an explicit cancel button; recognition concurrency (the actual requirement) is unaffected since tasks live server-side once created.
