# 按需阅读：存量项目文档重构（Remediation）

> DDE 不只服务从零开始的项目。大多数真实仓库是「文档已失控」的存量项目：散落的 md、没人敢删的旧设计稿、与代码脱节的 ADR、互相矛盾的 README。这份手册指导把混乱文档重构为「笔记 + 模块文档」体系。
>
> **铁律：勘察与计划阶段只读不写；未过用户确认门，绝不开始施工。**

## 0. 为什么必须先确认

文档重构是**重 token 操作**：每一篇要迁移的文档都要读全文、判定归属、改写为结构化笔记、跑校验。一个 200 篇文档的仓库，完整重构可能消耗数百万 token。

- 这不是躲懒的借口，而是**把钱花在刀刃上**的机制：先让用户看清规模与收益，再由用户拍板。
- 短期看 token 成本确实高；但对项目系统健康，这是一次性投入换长期复利——重构之后，每个新会话的 AI 都能在几分钟内检索到全部历史决策，不再重复踩坑、不再推倒重来。
- **用户拒绝确认门时，不软磨硬泡**：提供轻量替代（见 §3 末尾），然后停。

## 1. Phase 0 规模勘察（只读）

目标：30 分钟内给出「这个仓库的文档债务有多重」的可信数字。**此阶段禁止任何写入。**

盘点范围（用 rg / 文件遍历，不要逐篇精读）：

1. **文档清单**：`*.md` 总数、按目录分布（docs/、根目录、模块内 README、wiki/、adr/）。
2. **快速分类**（抽样标题与小节结构，每类抽 3–5 篇即可）：
   - 决策型（含「方案/选型/为什么」叙述）→ 笔记候选
   - 模块型（描述结构与职责）→ `docs/modules/` 候选
   - 入口型（README / 快速上手）→ 保留
   - 过期型（讲的功能代码里已不存在）→ 删除候选
   - 重复型（两篇讲同一件事）→ 合并候选
3. **代码锚点**：源码里 `// Note:` / `见 docs/` 类引用数量——它们是迁移时必须保活的链接清单。
4. **产出勘察表**（直接贴给用户）：

```text
| 类别 | 数量 | 典型样例 |
| 决策型 → 笔记候选 | 47 | docs/adr/0003-session-store.md |
| 模块型 → 模块文档候选 | 8 | docs/server-overview.md |
| 入口型 → 保留 | 3 | README.md |
| 过期型 → 删除候选 | 21 | docs/migration-2024.md |
| 重复型 → 合并候选 | 6 | a.md × b.md |
```

## 2. Phase 1 重构计划

产出一份**映射表 + 批次计划**，同样只读不写：

1. **逐篇映射**（决策型与重复型才需要逐篇；模块型按模块合并）：

```text
| 现有文档 | 去向 | 说明 |
| docs/adr/0003-session-store.md | 吸收 → implemented/architecture/<日期>-session-store.md | 拆出备选节；补 Scope: src/server/** |
| docs/server-overview.md | 改写 → docs/modules/server.md | 删掉其中的决策叙述，链接到笔记 |
| docs/migration-2024.md | 删除 | 功能已于 2025-03 下线 |
| a.md × b.md | 合并 → 一篇 rejected 笔记 | 保留更强理由的那篇的骨架 |
```

2. **批次划分**：按模块切批（一批 = 一个模块的笔记 + 它的模块文档），每批独立可验证。先做高被引/高风险的模块。
3. **验收标准**：每批结束后 `notes.ts verify` 全绿；原删除候选仅在替代笔记落盘后才删。

## 3. 确认门（必须，话术模板）

计划成形后，**必须**向用户完整呈现并等待明确同意。模板：

```text
我已完成勘察与重构计划（见上）。在开始前需要你确认：

📊 规模：约 {N} 篇文档待处理，其中 {A} 篇转为决策笔记、{B} 篇转为模块文档、
   {C} 篇合并、{D} 篇删除。分 {K} 批执行，每批结束跑一次校验。

💰 成本：这是一个重 token 操作，预计总消耗在 {档位区间}。
   短期看这笔费用不小；但这是对项目系统健康的一次性长期投资——
   重构完成后，之后每一个 AI 会话都能直接检索到结构化的历史决策，
   不再重复踩坑、不再误删承重墙、不再重提被否过的方案。

▶️ 请选择：
   1. 按计划全量执行
   2. 只执行第一批（{第一批内容}），看效果再决定后续
   3. 暂不执行
```

规则：

- 用户选 1 → 全量执行；选 2 → 只做第一批并在结束时再次询问；选 3 → 停止，不写任何文件。
- **确认门只能过一次**：施工开始后新增的范围（如发现的隐藏文档）先记录，批次收尾时一并请示，不自行动工。
- 轻量替代（用户选 3 时主动提供）：挑 3–5 篇最高风险的决策型文档手工转成笔记 + 建好目录骨架，其余留待将来。

## 4. Phase 2 分批执行

每批固定节奏：

1. **转换**：按映射表生成笔记（遵循 SKILL 格式：Problem / Decision 现在时 / Alternatives 必填 / Consequences 双面；补 `Scope:` 元数据）。原是提案未落地的 → `proposed/` 或 `rejected/`，不要伪造 implemented。
2. **模块文档**：每模块一份 `docs/modules/<模块>.md`，只写职责/边界/入口，决策链接指向笔记（见 references/module-wiki.md）。
3. **校验**：`npx tsx scripts/notes.ts verify`，红了当场修。
4. **保活锚点**：原代码注释里指向旧文档的引用，同批改指到新笔记路径。
5. **删除**：仅在该文档的全部有价值内容已被吸收、且引用已改完后执行。
6. **汇报**：本批完成 X 篇、失败 Y 篇及原因；然后进入下一批。连续两批校验无法转绿 → 停下来请示。

## 5. Phase 3 收尾

1. 全量 `notes.ts verify` 全绿；`notes.ts anchors` 检查代码锚点无悬空。
2. 生成看板（`notes.ts board --init`），让用户肉眼验收聚合效果。
3. 总结报告：转出多少笔记/模块文档、删了多少、剩余风险（如仍待迁移清单）。
4. 建议用户把「重要改动必带笔记」写进 `AGENTS.md`，防止债务回潮。

## 6. 成本估算档位表

估算给区间，不假装精确。token 消耗 ≈ 文档数 ×（读入 + 改写输出 + 校验修复）：

| 档位 | 待处理文档数 | 预估量级 | 建议策略 |
|---|---|---|---|
| S | < 30 | 数十万 token | 一批做完 |
| M | 30–100 | 数十万–百万级 | 2–4 批，按模块 |
| L | 100–400 | 百万–数百万级 | 先做高风险模块，其余分周推进 |
| XL | 400+ | 数百万级以上 | 只迁移「高被引 + 决策型」，其余归档原样保留 |

> 档位越高，越应该从确认门的「只做第一批」开始。
